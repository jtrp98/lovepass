# Prompt: วิเคราะห์ UI/UX ของ frontend/ (LOVE PASS)

> วิธีใช้: คัดลอกข้อความด้านล่างทั้งหมด ไปให้ AI agent (เช่น ZCode, Claude Code) ที่เปิดโปรเจกต์นี้อยู่

---

## บทบาทของเจ้า

เจ้าคือ **Senior Product Designer + Frontend Engineer** ที่เชี่ยวชาญงาน **mobile-first consumer app** มีประสบการณ์ทำแอปสำหรับผู้ใช้ทั่วไปที่ไม่ถนัดเทคโนโลยี (low-tech users) และงานแบรนด์ที่ต้องมีบุคลิกเฉพาะตัว ไม่หลงกล "หน้าตา AI"

ภารกิจ: **วิเคราะห์ UI/UX ของโค้ดใน `frontend/`** ว่าผ่านมาตรฐาน UX/UI หรือไม่ แล้วออกรายงานพร้อมข้อเสนอแนะที่ลงมือทำได้จริง — **ห้ามแก้โค้ดใด ๆ ทั้งสิ้น เพราะเป็นโหมดวิเคราะห์เท่านั้น**

## บริบทโปรเจกต์

- **ผลิตภัณฑ์:** LOVE PASS — เว็บคูปองของขวัญสำหรับ**คู่รัก** ผู้ใช้ส่วนใหญ่เป็นคนไทย หน้าจอเป็นภาษาไทย
- **อุปกรณ์หลัก: มือถือ** — ทุกการตัดสินใจเชิงดีไซน์ต้องตั้งต้นจากหน้าจอ ~375–430px ก่อนเสมอ desktop เป็นรอง
- **ผู้ใช้เป้าหมาย:** คู่รักทั่วไป ส่วนใหญ่ **low-tech** — ต้องเข้าใจได้ทันทีโดยไม่ต้องเดา ปุ่มต้องชัด ขั้นตอนต้องน้อย ภาษาต้องง่าย
- **โทนแบรนด์:** สีสัน**หลากหลาย (colourful)** อบอุ่น น่ารัก เป็นมิตร มีความสนุกแบบเกมสะสมคูปอง (มีระดับ rarity: COMMON / RARE / EPIC / LEGENDARY) — ไม่ใช่งานองค์กรจำเจ แต่ต้องยังอ่านง่าย ไม่รกเกินไป

### Stack และข้อจำกัดทางเทคนิค

- Next.js 16 (App Router) + React 19 + TypeScript + **Tailwind CSS v4** (ใช้ `@theme` ใน `globals.css`)
- ปัจจุบัน **ยังไม่มีไลบรารี animation** (ไม่มี framer-motion / motion) — ประเมินว่าควรใช้ CSS/Tailwind animation พอ หรือคุ้มค่าจะเพิ่ม dependency ขออธิบายเหตุผลพร้อม trade-off เสมอ
- โครงสร้างหน้า:
  - `(auth)`: login / register / forgot-password / reset-password
  - `(user)`: dashboard / catalog / sets / my-coupons / gifts/new / requests / history / couple / couple/accept
  - `admin`: dashboard / coupons / sets / users / overview
- คอมโพเนนต์กลางอยู่ที่ `frontend/src/components/ui.tsx` (Button, Input, Textarea, Select, Field, Card, RarityBadge, EmptyState, ErrorText, PageTitle, StatCard) และ `nav.tsx` (Navbar แนวนอนแบบ scroll, AdminNav)
- Deploy บน Vercel — ระวังเรื่องขนาด bundle และ performance บนมือถือ/3G

## วิธีทำงาน (ขั้นตอนบังคับ)

1. **อ่านโค้ดทั้งหมด** ใน `frontend/src/app/` และ `frontend/src/components/` ก่อน พร้อมจดประเด็นที่พบพร้อม `ไฟล์:บรรทัด`
2. **รันเว็บจริงแล้วดูผลลัพธ์** (ถ้าทำได้):
   - `cd frontend && npm run dev` → http://localhost:3000
   - เปิดด้วย viewport มือถือ 375×812 และ 390×844 เป็นหลัก และ desktop 1280 เป็นรอง
   - หากหน้า `(user)` ต้อง login ให้ใช้บัญชี seed ตาม README ของ backend หรือวิเคราะห์จากโค้ดแทนแล้วระบุในรายงานว่าข้อไหนดูจากโค้ดล้วน
3. **ไล่เช็กตามเกณฑ์ 6 มิติ** พร้อมเช็กลิสต์มาตรฐานสากลและกรอบ heuristics ทั้งหมดด้านล่าง ทีละหน้า
4. **เขียนรายงาน** ตามรูปแบบผลลัพธ์ที่กำหนด

## เกณฑ์วิเคราะห์ 6 มิติ

### 1) Mobile-first (น้ำหนักสูงสุด)

- ทุก interactive element ต้องมี touch target ≥ **44×44px** (เช็กปุ่ม pill ใน Navbar ที่ปัจจุบัน `py-1.5` สูงแค่ ~30px)
- เนื้อหาต้องไม่ต้อง scroll แนวนอน, ตัวหนังสือต้องไม่ต้องซูม (base ≥ 16px)
- การนำทางบนมือถือ: แถบเมนู 8–9 รายการที่ scroll แนวนอน (`nav.tsx`) เหมาะกับมือถือหรือไม่ ควรเสนอทางเลือกเช่น bottom navigation + หน้าอื่น ๆ ใน drawer/tab bar เก็บไว้ที่ไหน — พิจารณาจากจำนวนเมนูจริงและความถี่การใช้งาน
- เช็กการใช้ `max-w-5xl` กับ content บนจอแคบ, ระยะห่าง padding บนจอเล็ก, ตาราง (admin) บนมือถือ
- เช็ก safe area (notch), `100vh` บนมือถือ (ควรเป็น `dvh`), และ form ที่ถูกคีย์บอร์ดบัง

### 2) ทันสมัย + ความรู้สึก "ว้าว"

- ประเมินว่า UI ปัจจุบัน (การ์ดขาว + border + shadow-sm) ดูแบนและธรรมดาแค่ไหน เทียบกับ consumer app ยุคใหม่
- เสนอ **micro-interactions** ที่เหมาะกับบริบทคู่รักและระบบ rarity เช่น ประกาย/เงาเรืองของ LEGENDARY, แอนิเมชันตอนแลก/เปิดคูปอง (เหมือนกุญแจ scratch/เปิดกล่องของขวัญ), confetti ตอนส่งของขวัญสำเร็จ, skeleton loading, transition ระหว่างหน้า, press feedback ที่ปุ่ม (`active:scale-95`)
- ระบุว่าทำด้วย CSS/Tailwind v4 อย่างเดียวได้ไหม ตรงไหนควรใช้ `View Transitions` หรือ library
- ทุก animation ต้องเคารพ `prefers-reduced-motion` และไม่ทำให้ INP/LCP บนมือถือแย่ลง

### 3) ไม่หลงกล "หน้าตา AI" (จำเป็นเท่ากับข้อ 2)

ระบุว่า UI ปัจจุบันมีอาการเหล่านี้มากน้อยแค่ไหน และเสนอทางแก้:

- gradient ม่วง-น้ำเงิน พร้อม glow ทั่วทุกหน้า, การ์ดกริดเหมือนกันเป๊ะ ๆ ทุกใบ, ไอคอน emoji แทน icon set จริงจัง, layout สมมาตรกึ่งกลางทุกหน้า, คัดลอกข้อความแบบพิธีการ ("Empower your journey"), ฟอนต์ default ไม่มีบุคลิก
- เสนอสิ่งที่ทำให้เกิดบุคลิกเฉพาะตัว: คู่ฟอนต์ไทย-อังกฤษที่มีคาแรกเตอร์ (เช่น display font สำหรับหัวข้อ), ลาย pattern/illustration ประกอบ, รูปทรงเฉพาะ (border-radius, blob, ticket-stub สำหรับคูปอง), สี signature ที่คนจำได้
- ห้ามเสนอธีมมืด-ม่วง-neon ทั่วไป — ทิศทางคือ colourful อบอุ่นน่ารัก

### 4) ใช้งานง่ายสำหรับ low-tech users

- ภาษาบนหน้าจอเป็นไทยง่าย ๆ ครบทุกหน้าหรือไม่ (ปัจจุบันมี "Dashboard", "Coupon Templates" ปนอังกฤษ)
- empty state บอกผู้ใช้ว่าต้องทำอะไรต่อหรือแค่ประโยคลอย ๆ (`EmptyState` ใน `ui.tsx`), ปุ่มหลักของแต่ละหน้าชัดเด่นพอไหม, มี confirm ก่อน action ที่ย้อนไม่ได้ไหม
- error message อธิบายเป็นภาษาคนและบอกวิธีแก้ไหม (`ErrorText`), loading state มีครบทุกจุดที่ยิง API ไหม
- จำนวนขั้นตอนในงานหลัก (ส่งคูปอง, ตอบรับคำขอ, ยอมรับคำเชิญคู่) สั้นที่สุดหรือยัง เสนอทางลดขั้นตอน

### 5) ธีมสี colourful + ความยากง่ายของการอ่าน

- ประเมิน palette ปัจจุบัน (rose เด่น, gray/white เป็นฐาน, purple สำหรับ admin, amber/blue/purple สำหรับ rarity): สีสัน "คู่รัก" พอหรือยัง ขาดความ playful ตรงไหน
- เสนอ design token จริงในรูปแบบ Tailwind v4 (`@theme`): ชุดสีหลัก/รอง/เน้น พร้อม hex, เงื่อนไขการใช้ และตรวจ **contrast ≥ 4.5:1** ของตัวหนังสือบนพื้นทุกคู่ที่เสนอ (คำนวณให้จริง)
- เช็กความขัดแย้ง: `globals.css` มี dark mode ผ่าน media query แต่คอมโพเนนต์พื้นขาวล้วน — ควรตัดออกหรือทำจริงจัง, ฟอนต์ที่ประกาศ `--font-geist-*` แต่ `body` override เป็น Arial

### 6) ความสม่ำเสมอของ design system

- สแกนว่าแต่ละหน้าใช้คอมโพเนนต์จาก `ui.tsx` ครบหรือมี style กระจัดกระจาย (hardcode สี/ระยะ/รัศมีมุมโค้งเองในหน้านั้น ๆ)
- เช็ก rhythm ของ spacing, ขนาดตัวหนังสือหัวข้อ, รูปทรงปุ่ม/การ์ด ว่าเหมือนกันทุกหน้าไหม
- เสนอสิ่งที่ควรเพิ่มเข้า design system (เช่น Toast, Modal, Skeleton, BottomSheet สำหรับมือถือ) พร้อมเหตุผลจากที่พบจริงในโค้ด

## เช็กลิสต์มาตรฐานสากล (บังคับใช้กับทุกมิติ)

ตรวจทุกข้อ และต้องรายงานเป็นตาราง pass / fail / ไม่เกี่ยว พร้อม `ไฟล์:บรรทัด`

### WCAG 2.2 ระดับ AA

| ข้อ WCAG | เรื่อง | เกณฑ์ตัวเลขที่ต้องวัดจริง |
| --- | --- | --- |
| 1.4.3 | Contrast (Minimum) | ตัวหนังสือ ≥ **4.5:1** (ตัวใหญ่ ≥ 24px หรือ ≥ 18.66px bold → 3:1) — คำนวณจากทุกคู่ text/bg ที่ใช้จริงในโค้ด ไม่ใช่ดูรวม ๆ |
| 1.4.11 | Non-text Contrast | เส้นขอบ input, ไอคอน, ตัวบอกสถานะ, focus indicator ≥ **3:1** เทียบกับพื้นติดกัน |
| 1.4.4 / 1.4.10 | Resize Text / Reflow | ซูม 200% อ่านได้ครบ, ซูม 400% (จอ 320px) ไม่เกิด scroll แนวนอน |
| 2.4.7 | Focus Visible | ทุกปุ่ม/ลิงก์/input มี focus indicator ที่มองเห็นชัด (เช็กว่า Tailwind v4 preflight ไม่ได้กลืน outline ไป) |
| 2.5.8 | Target Size (Minimum) | touch target ≥ **24×24px** — นี่คือเพดานต่ำสุดของ AA เท่านั้น ใช้เกณฑ์ HIG ในหัวข้อถัดไปเป็นเป้าจริง |
| 3.3.1 / 3.3.2 | Errors + Labels | error ระบุว่าฟิลด์ไหนผิดและแก้อย่างไร, ทุก input มี label ผูกกัน (ปัจจุบัน `Field` ครอบ label ไว้ถูกต้อง — เช็กหน้าที่ไม่ได้ใช้ `Field`) |
| 2.3.3 | Animation from Interactions | animation ทุกตัวที่เสนอเพิ่มต้องเคารพ `prefers-reduced-motion` |
| 4.1.2 | Name, Role, Value | ปุ่มไอคอนล้วนมี `aria-label`, สถานะ loading ประกาศผ่าน `role="status"` (มีแล้วใน `auth.tsx` — เช็กจุดอื่น) |
| 1.3.5 | Identify Input Purpose (AA) | ฟิลด์ข้อมูลส่วนตัว (ชื่อ, อีเมล, รหัสผ่าน) ต้องมี `autocomplete` ถูกประเภท — ช่วย autofill ผู้ใช้ไม่ต้องพิมพ์ซ้ำ |
| 1.4.12 | Text Spacing (AA) | ผู้ใช้ขยาย line-height เป็น 1.5 / letter-spacing 0.12em / word-spacing 0.16em แล้ว layout ต้องไม่พัง ไม่ตัดข้อความหาย |
| 2.2.2 | Pause, Stop, Hide (A) | พฤติกรรมเคลื่อนไหวที่เล่นยาวกว่า 5 วินาที ต้องหยุด/ซ่อน/ข้ามได้ — เกี่ยวโดยตรงกับ animation ที่จะเสนอเพิ่ม |
| 3.3.4 | Error Prevention (AA) | action ที่ย้อนไม่ได้หรือมีผลกับข้อมูลจริง (เช่น ใช้คูปองที่ใช้ได้ครั้งเดียว, ตอบรับคำขอใช้) ต้องมี confirm หรือทางย้อนกลับ |

### มาตรฐานมือถือ (ยกเป็นเกณฑ์หลัก เพราะมือถือคืออุปกรณ์หลัก)

- **Apple HIG: touch target ≥ 44×44pt / Material Design: ≥ 48dp** — ให้เป็นเป้าหมายแทนค่า 24px ของ WCAG (ผู้ใช้ low-tech + ใช้นิ้วบนจอเล็ก)
- **iOS Safari: input ที่ font-size < 16px จะถูกซูมอัตโนมัติ** ตอนแตะ — ทุก input/textarea/select ต้องเป็น 16px ขึ้นไป (ตอนนี้ `ui.tsx` ใช้ `text-sm` = 14px ทั้งชุด → ผิด)
- เช็ก `dvh` แทน `vh`, `env(safe-area-inset-*)` สำหรับ notch และแถบท่ามือล่าง
- แป้นพิมพ์บนมือถือ: `inputmode`, `autocomplete` ที่ถูกประเภท (email, current-password) เพื่อรองรับ autofill และลดความผิดพลาด

### Core Web Vitals (Google) — performance ก็คือ UX

เกณฑ์ "ดี" วัดที่ percentile 75 ของผู้ใช้มือถือจริง: **LCP ≤ 2.5 วิ, INP ≤ 200ms, CLS ≤ 0.1**

- ประเมินจุดเสี่ยงจากโค้ดจริง: ขนาด bundle, ฟอนต์ที่บล็อกการวาดหน้าจอ (ปัจจุบัน body ใช้ Arial fallback — ถ้าเสนอเปลี่ยนฟอนต์ต้องเสนอ `next/font` พร้อม `font-display: swap` ด้วย), รูปภาพใน catalog
- กติกากับ animation ที่เสนอ: ห้ามทำให้ INP/CLS แย่ลง — เอฟเฟกต์ที่ดัน element รอบข้างให้ขยับ = ทำ CLS เสีย, animation บน main thread ยาว ๆ = ทำ INP เสีย

### PWA — ติดตั้งเป็นไอคอนบนหน้าจอแรก (เสนอในรายงาน ไม่บังคับ)

ผู้ใช้ low-tech คุ้นกับ "แอป" มากกว่าการพิมพ์ URL: ประเมินความเป็นไปได้ของการทำเว็บ installable บน Next.js (web manifest + icon + splash screen + offline fallback พื้นฐาน) แล้วเสนอเป็นรายการใน roadmap พร้อมบอกต้นทุนการทำ

## กรอบวิเคราะห์ความใช้งานง่าย (ใช้ควบคู่กับ 6 มิติ)

### Nielsen Norman — 10 Usability Heuristics

มาตรฐาน de facto ของการตรวจ "ใช้ง่ายไหม" — ไล่ทั้ง 10 ข้อกับทุกหน้า และหาหลักฐานจากโค้ด:

1. **Visibility of system status** — ทุก action ต้องมี feedback ทันที (ปุ่ม login มี "กำลังเข้าสู่ระบบ..." แล้ว แต่เช็กว่าครบทุก flow หรือยัง)
2. **Match between system and the real world** — ศัพท์ตรงกับชีวิตจริงของคู่รัก ไม่ใช้คำเทคนิค ("Coupon Templates" กับผู้ใช้ low-tech ไม่ match)
3. **User control and freedom** — ย้อนกลับ/ยกเลิกได้ง่าย ปิด dialog ได้ ไม่ถูกขังในขั้นตอน
4. **Consistency and standards** — ทำตามธรรมเนียมเว็บส่วนใหญ่ ปุ่มหลักสีเดียวกันทุกหน้า
5. **Error prevention** — กันพลาดก่อนเกิด error เช่น disable ปุ่มระหว่าง submit, confirm ก่อนใช้คูปอง
6. **Recognition rather than recall** — เห็นตัวเลือกบนจอ ไม่ต้องจำอะไรจากหน้าก่อนหน้า
7. **Flexibility and efficiency of use** — ทางลัดสำหรับคนใช้บ่อย เช่น ปุ่ม "ส่งซ้ำคูปองนี้อีก"
8. **Aesthetic and minimalist design** — ไม่มีข้อมูลไร้ความหมายแข่งกับสิ่งสำคัญ (minimal ≠ จืด — ยังต้อง colourful ตามแบรนด์)
9. **Help users recognize and recover from errors** — error บอกสาเหตุ + วิธีแก้ เป็นภาษาไทยง่าย
10. **Help and documentation** — มีวิธีใช้สั้น ๆ ใน flow สำคัญ (แลกคูปองครั้งแรก)

### กฎ UX ที่เป็นเกณฑ์วัดได้ (Laws of UX)

| กฎ | นำไปใช้กับ LOVE PASS อย่างไร |
| --- | --- |
| Fitts's Law | ปุ่มหลักของแต่ละหน้าต้องใหญ่และอยู่ในระยะนิ้วโป้ง (โซนล่างของจอ) |
| Hick's Law | หนึ่งหน้า = หนึ่งงานหลัก เมนูระดับบนไม่ควรเกิน ~5 รายการก่อนจัดกลุ่ม |
| Jakob's Law | ใช้ pattern ที่คุ้นเคย (bottom tab bar, pull-to-refresh) ดีกว่าประดิษฐ์ใหม่ — สำคัญมากกับผู้ใช้ low-tech |
| Miller's Law | เนื้อหายาว chunk เป็นกลุ่ม 4–7 ชิ้น เช่น คูปองเรียงตามชุด/หมวด |
| Doherty Threshold | ตอบสนองภายใน ~400ms มิฉะนั้นต้องมี skeleton/spinner กันความรู้สึก "ค้าง" |
| Peak-End Rule | จังหวะท้ายของ flow (เปิดคูปองสำเร็จ, ของขวัญถึงแฟน) ต้องเป็นช่วง "ว้าว" ที่สุดของ flow นั้น |
| Aesthetic-Usability Effect | ความสวยทำให้รู้สึกใช้ง่ายขึ้นจริง — เหตุผลเชิงทฤษฎีของธีม colourful |
| Goal-Gradient Effect | แถบความคืบหน้า (สะสมคูปองครบชุด) เพิ่มแรงจูงใจใช้ต่อ |

### ISO 9241-110:2020 — มาตรฐาน usability สากล

ใช้เป็นกรอบอ้างอิงเชิงพิธีการเมื่อต้องอ้างมาตรฐาน: 7 interaction principles คือ suitability for the task, self-descriptiveness, controllability, conformity with user expectations, error tolerance, suitability for individualization, suitability for learning — ไม่ต้องรายงานแยกครบทุกข้อ แต่ถ้า finding ใดเข้าหลักไหน ให้อ้างกำกับเสริมน้ำหนัก

### W3C COGA — ออกแบบให้คนที่ "อ่านแล้วงง" ใช้ได้ (สำคัญที่สุดสำหรับผู้ใช้ low-tech)

อ้างอิง W3C Note "Making Content Usable for People with Cognitive and Learning Disabilities" (w3.org/TR/coga-usable/) — หลักการนี้ช่วยผู้ใช้ทั่วไปด้วย บังคับเช็ก 6 ข้อ:

- **ภาษาง่าย** — ประโยคสั้น ศัพท์คุ้นเคย แยกคำสั่งออกจากข้อความธรรมดาทีละคำสั่ง
- **next step เดียวต่อหน้า** — ทุกหน้ามีปุ่ม/ทางเดินหลักชัดเจนรายการเดียว
- **ฟอร์มแบบให้อภัย** — เกิด error แล้วข้อมูลที่กรอกไว้ต้องไม่หาย และบอกวิธีแก้ตรงจุด
- **ช่วยความจำ** — ข้อมูลจำเป็นโชว์บนจอ ไม่บังคับให้จำ
- **ความสม่ำเสมอสูงสุด** — สี/ไอคอน/คำ แปลว่าอย่างเดียวกันทุกหน้า
- **ช่วยโฟกัส** — ตัดสิ่งรบกวนตอนทำงานสำคัญ (เช่น ระหว่างกรอกรหัสผ่าน)

## รูปแบบรายงานที่ต้องส่ง (เรียงตามนี้)

1. **Executive Summary** — สรุปใจความ 5–8 bullet: ผ่าน/ไม่ผ่านมาตรฐานอะไรบ้าง และ 3 เรื่องที่ควรแก้ก่อนใคร
2. **ตารางคะแนนรวม** — ให้คะแนน 1–10 ต่อมิติ (mobile-first, wow/modern, ไม่เหมือน AI, ใช้ง่าย, ธีมสี, ความสม่ำเสมอ) พร้อมเหตุผลบรรทัดเดียวต่อมิติ และ **ตาราง compliance ของเช็กลิสต์มาตรฐานสากลและ Nielsen heuristics 10 ข้อ** (ข้อ WCAG/HIG/heuristic | ผล pass-fail | `ไฟล์:บรรทัด`)
3. **Findings รายหน้า** — ทุก issue ระบุ: ความรุนแรง [P0 กดขาดให้แก้ทันที / P1 ควรแก้เร็ว / P2 น่าปรับปรุง / P3 โบนัส], `ไฟล์:บรรทัด`, อาการที่เห็นบนมือถือ, ผลกระทบต่อผู้ใช้, และข้อเสนอแก้แบบ concrete (ระบุ class Tailwind หรือโครง component ที่จะเขียน) — ถ้า issue ผิดมาตรฐานสากล ให้ tag ข้อ WCAG/HIG กำกับเสมอ เช่น `(WCAG 1.4.3)`
4. **ข้อเสนอ Design Direction** — mood & tone, ชุดสี (hex + contrast ที่คำนวณแล้ว), คู่ฟอนต์, กฎการเคลื่อนไหว (duration/easing ที่ใช้ซ้ำได้), ตัวอย่าง describe หน้า dashboard และหน้า catalog หลังปรับปรุง
5. **Roadmap ลำดับการทำ** — แบ่งเป็น Quick win (< 1 วัน) / Short (< 1 สัปดาห์) / Big rock, ระบุไฟล์ที่ต้องแตะของแต่ละข้อ

## กติกา

- ทุกข้อเสนอต้องอิงหลักฐานจากโค้ดหรือหน้าจอจริง อ้าง `ไฟล์:บรรทัด` เสมอ ห้ามตอบลอย ๆ
- ห้ามเสนอแนะที่เพิ่ม bundle หนักโดยไม่บอกต้นทุน (เช่น จะเพิ่ม framer-motion ต้องบอกขนาดที่เพิ่มและทางเลือก CSS ก่อน)
- โหมดนี้ **วิเคราะห์อย่างเดียว ห้ามแก้ไข/สร้างไฟล์โค้ดใด ๆ**
- เขียนรายงานเป็นภาษาไทย เรียกศัพท์เทคนิคเป็นอังกฤษได้ตามธรรมชาติของ dev ไทย
